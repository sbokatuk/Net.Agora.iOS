## What's changed

First release of `Net.Agora.Video.iOS`: .NET for iOS / .NET MAUI bindings for the Agora Video
(RTC) iOS SDK — the "RtcBasic" subspec of **AgoraRtcEngine_iOS 4.6.2**, the same artifact
`pod install` would fetch, downloaded straight from Agora's SDK release URL and verified against a
SHA-256 pinned in `build/checksums.txt`.

> **Package versions are `<AgoraRtcEngine_iOS pod version>.<binding revision>`.** `4.6.2.1` is
> AgoraRtcEngine_iOS `4.6.2`, binding revision `1`. The fourth component belongs to this
> repository and advances when the binding or packaging changes while the native SDK stays put.
> The iOS pod and the Android Maven artifact for the same product are released on independent
> schedules, so this version is not expected to match `Net.Agora.Video.Android`'s.

## What is bound, and why by hand

Objective Sharpie's bundled clang cannot parse any Xcode SDK from 15.3 onward, so
`ApiDefinition.cs` and `StructsAndEnums.cs` are hand-written against the real headers
(`AgoraRtcEngineKit.h`, `AgoraObjects.h`, `AgoraEnumerates.h`), scoped to what the cross-platform
[`Net.Agora`](https://github.com/sbokatuk/Net.Agora) client needs: create the engine, join/leave a
channel, publish/mute audio and video, render local/remote video, and the matching delegate
callbacks. Most apps want that cross-platform client; reach for this package directly only when
you need something it does not expose.

The package targets `net8.0-ios18.0`, `net9.0-ios18.0` and `net10.0-ios26.0`. No single .NET SDK
builds all three, so the build packs twice and merges the results — see `build/merge-packages.py`.
**No Mac Catalyst**: Agora ships no `maccatalyst` slice for this SDK.

Six dynamic xcframeworks travel beside the binding assembly as a compressed `.resources.zip`:
`AgoraRtcKit` plus the codec/infra frameworks its binary links against (`aosl`, `Agorafdkaac`,
`Agoraffmpeg`, `AgoraSoundTouch`, `video_dec`). `video_dec` is the one worth remembering:
AgoraRtcKit links it directly, so a package without it kills every consuming app at launch — a
dyld failure nothing at compile or link time can see. It was found by running a consuming app
on-device, and it is now pinned by tests at both layers below.

## Tests

**Package-layout checks** run against the packed `.nupkg`, not the build output: a binding
assembly and a native payload for every target framework, all six xcframeworks present, the
payload logically identical across target frameworks (which is what would catch a mismatched
net10 merge graft), iOS device + simulator slices only, xcframework manifests that match the
slices actually shipped, and a size floor that rules out an empty placeholder payload.

**An on-simulator suite** (`tests/Net.Agora.iOS.DeviceTests`) installs the **packed package** into
a real iOS app and drives the raw binding: it asserts all six native frameworks are actually
loaded into the process, reads the native SDK version through the Objective-C runtime, constructs
`AgoraRtcEngineKit` with a syntactically-valid unregistered App ID, enables/disables and mutes
audio and video, sets the channel profile and client role, attaches and detaches a local video
canvas, and destroys the engine. Nothing touches the network and no credentials are involved —
the façade repository's own device tests cover the join path.

## Sample

`samples/Net.Agora.Sample.iOS` is a MAUI app (iOS only) that joins a channel and publishes/renders
video directly against `AgoraRtcEngineKit` — an App ID/channel/token entry, Join/Leave buttons,
and a local + remote video view backed by a hand-rolled MAUI handler, which is exactly what a
consumer skipping the cross-platform façade has to wire up. It consumes the packed package from
`./artifacts`, so it doubles as proof the package restores and links as published.

## CI

Pull requests pack, validate, build the sample and run the simulator suite against both extreme
target frameworks (`net8.0-ios18.0` and `net10.0-ios26.0` — net9 comes out of the same pack pass
as net8), then publish a `-beta.<pr>.<run>` prerelease; tagging `v4.6.2.1` publishes the package
and creates a GitHub release. Publishing uses nuget.org trusted publishing, so there is no
long-lived API key.
